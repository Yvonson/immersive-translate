# YouTube 评论译文夹杂界面文字：排查与修复

日期：2026-10-17。版本保持 `0.2.0` / `0.2.0-preview.1`。

## 用户反馈与结论边界

用户反馈一条日文评论的中文译文末尾出现原文没有的“合集、了解细节”，并确认使用 Google 翻译。尚未提供原视频链接，因此没有取得这条评论当时的 DOM 和请求，不能断言这两个词在原页面上的具体位置。

本次发现并修复了两条能够复现此现象的正文提取路径。构造样本的请求日志证明，污染会在发送到翻译引擎之前发生。未对译文进行关键词删除，也未切换翻译服务。

## 发现的缺陷

1. **隐藏节点被当作正文。** 原 `snapshot()` 遍历文本节点时，没有排除 `hidden`、CSS 隐藏和工具提示。隐藏的 `<span>` 与正文一起被送去翻译；重新构造译文行内标签时只复制字体、颜色等样式，没有复制隐藏状态，于是原来不可见的文字显示在译文中。
2. **行内评论越过正文边界。** YouTube 的 `#content-text` 可以是行内自定义元素。原 `resolve()` 优先寻找通用块级祖先，可能越过已配置的正文节点，取到同时包含作者、时间和工具栏的父区域。构造样本中，正文请求包含了邻近的作者、时间和推荐标签，译文也插在错误的父区域之后。
3. **原样保留的代码也存在同类风险。** 原代码片段通过 `textContent` 重建，会重新显示代码内部的隐藏说明。现在代码、按键及时间等保留片段也使用过滤后的快照文本，并参与内容变更检测。

Google 返回额外文字、接口解析混入数据、其他扩展改写页面也是可能性。本轮同一 Google 接口的实际请求未出现这两个尾词，尚无证据将其归因于 Google 服务；也没有证据表明原页面存在另一个扩展干扰。

## 修复行为

- 在提取阶段排除隐藏、inert、工具提示、菜单、按钮及常见屏幕阅读辅助节点；保留正常可见的行内格式和 `display:contents` 子内容。
- 将站点明确指定的文字节点作为向上查找的边界，覆盖 Ctrl 与整页翻译。
- 用内部 `WeakSet` 区分插件为“仅译文”模式创建的原文隐藏包装，保证过滤不会把插件自己的原文记录误判为空。
- 监听正文相关的显隐属性变化，展开后重新读取，隐藏后移除对应译文内容；无关播放器样式更新不会触发整页正文扫描。
- 正常正文中确实出现“合集、了解细节”时继续翻译，不建立尾词黑名单。翻译服务、配置格式和密钥存储不变。

## 验证证据

**修复前的构造样本：** 浏览器回归捕获的翻译请求包含隐藏的“合集、了解细节”和工具提示；另一个行内评论样本包含相邻作者、时间和工具栏。两个用例均按预期失败。

**修复后的自动化：** `npm test` 12 项、`npm run test:browser` 15 项通过，构建和产物检查通过。新增用例覆盖 Google HTML 请求、隐藏元数据、正文边界、Ctrl/整页、动态显隐、隐藏说明变化、正常同名正文、格式、代码和仅译文模式。

**真实 Google：** 在隔离 Chromium 中，将用户提供的日文以纯文本、带插件格式标记两种形式发送到当前扩展的同一 Google 接口；读取原始响应与插件解析结果，两者均无“合集、了解细节”，格式标记保留。这是这组文本请求的验证，不代表 Google 所有输入都不会产生翻译错误。

**真实 YouTube 结构：** 无登录 Chromium 查看[公开样本](https://www.youtube.com/watch?v=EWX0bbGAd0k)，确认 `#content-text` 为 `YT-ATTRIBUTED-STRING`，计算样式为 `display:inline`。采样评论没有隐藏子节点；此样本用于确认行内边界问题，不能替代用户原评论现场。

## 使用与后续诊断

重新加载更新后的扩展，并刷新 YouTube 页面后再翻译。新正文路径仅使用内存缓存，重新加载会建立新会话，无须清除模型密钥。

若同一评论仍出现问题，下一步需要原视频链接，分别比对可见正文、提取请求、Google 原始响应和最终译文。记录应避开 Key 和个人浏览器数据；不要用删除特定尾词掩盖新的来源污染。
